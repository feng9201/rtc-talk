# RK3576 对讲客户端开发计划

> 范围：RK3576 / Buildroot / Qt5，一期纯音频。
> 依据：现有项目计划、信令协议、服务端 S2 代码、libwebrtc 构建记录及本次实机检查。
> 当前状态：环境摸底完成；客户端业务工程尚未创建，以下 C0～C7 均待实施。
> 仓库归档目标：`plan/rtc-client-dev-plan.md`。本轮只制定计划，不执行工程搭建、部署或设备配置修改。

## 1. 目标与范围

### 已确定的技术路线
- 界面使用 **Qt5 Widgets**，不采用 Web UI，也不引入 QML/Qt Quick 依赖。
- 采用用户确认的 **B 路线：websocketpp，经 vcpkg 管理依赖**；客户端 WS 不使用 libdatachannel，也不使用 QWebSocket。
- `talk-core` 同时包含信令、房间状态和媒体引擎，保持纯 C++、不依赖 Qt；Qt 只承担展示与交互。
- 媒体使用 Google libwebrtc M146：ADM、APM、Opus、NetEQ、ICE、DTLS-SRTP；不另建音频编码或抖动缓冲链路。
- 客户端使用标准 SDP，对接现有服务端适配层，不引入 libmediasoupclient。

### 交付分界
1. **首个可用版本：C0～C4**——RK3576 上通过 Qt5 界面加入房间、双向通话、静音、选择音频设备及调节播放音量，对接 S2。
2. **一期功能完整版本：C5～C7**——增加呼叫、P2P/SFU 切换、PTT、主持人控制、恢复与长稳测试，对接 S3～S5。
3. 二期再接 RK MPP 视频编解码、sbdc 解码/显示链路；一期仅保留媒体扩展边界，不接入 sbdc、miniaudio 或旧 webrtc_back 业务代码。

## 4. 构建与依赖设计

### 4.1 工具链和 vcpkg
- 使用 CMake 3.28.3、Buildroot GCC 12.4；媒体封装及核心代码采用 C++20，不使用 GCC 12 尚未提供的 `std::format`。
- 通过 `CMAKE_TOOLCHAIN_FILE` 接入 vcpkg，再 chainload 客户端自己的 RK toolchain；设置专用 triplet `arm64-rk3576`、host triplet `x64-linux`。
- 显式设置 sysroot，目标库/头文件/包只从目标路径解析，构建工具从宿主路径解析。不得混入宿主 `/usr/lib` 的 x86 库。
- 复用 sbdc 的工具链位置与配置经验，但**不照搬**其全局 `--allow-shlib-undefined`、`--Bsymbolic` 或通用 `arm64-linux` 缓存；链接错误必须在构建期暴露。
- vcpkg 根目录参数化，当前可用入口为 `/home/wdz/projects/cuiqiusong/vcpkg`；以当前提交 `d4d39d71b3e6dd7536592c36ab2f7e84a8a64942` 为初始锁定基线，并在 C0 验证相关 port 与工作树一致。
- 最小依赖：`websocketpp`、独立 `asio`、`nlohmann-json`。websocketpp 设置 `default-features:false`，使用非 TLS Asio transport 与 `ASIO_STANDALONE`，不因默认 recommended feature 引入 Boost/OpenSSL/zlib。
- 当前 websocketpp port 为 `0.8.2#2`，包含 C++20 修补；C0 必须编译握手样例验证，不以“header-only”代替兼容性测试。
- Qt5 直接使用 RK sysroot 的版本，不从 vcpkg 重编 Qt；UI 链接 Core/Gui/Widgets/Network，不链接 Qt5WebSockets。

### 4.2 libwebrtc 接入
采用已验证的 SDK 交付形式甲：外部 `libwebrtc.a` 加匹配头文件；客户端再将其静态链接到 `libtalk_core.so` 内部。这与 talk-core 对外提供共享库/C API 不冲突。

开发期通过本地配置传入：
- `RK3576_HOST=/opt/rockchip/rk3576/host`
- `WEBRTC_SOURCE_DIR=/home/wdz/projects/hxf/webrtc_m146/src`
- `WEBRTC_BUILD_DIR=/home/wdz/projects/hxf/webrtc_m146/src/out/rk3576_release`

构建约束：
- 使用同一次构建的库、头文件、GN defines；导入 Abseil/libyuv 所需 include，不把整个源码树复制进 Git。
- GCC 链接使用非 ThinLTO、非 CREL 的 Release 库，不误用 `rk3576_lto` 产物。
- `-fno-rtti` 仅应用到需要继承 WebRTC 接口的实现目标，不全局影响 Qt 或其他代码；异常不得跨 C API 边界。
- 验证静态对象适合链接共享库，开启隐藏符号和版本脚本，仅导出 `talk_*`；使用 `--gc-sections`，保留独立调试符号。
- C0 同时验证 Qt 宿主生成工具、目标 Qt 库、libstdc++ ABI 及最终板端动态装载。
- Qt 程序体积与核心库体积分开统计，不将旧探针的 8MB 目标直接套到整个 GUI 发布包。

### 4.3 配置与认证
- 服务地址、房间、用户标识、音频设备、音量、日志级别通过运行配置提供，不写死在业务代码中。
- core 接受外部传入/更新的 token；CLI 支持受限权限 token 文件，保持完整 headless 工作能力。
- Qt 测试界面可用 QtNetwork 从 `/dev/token` 获取开发 token，仅在显式开发模式启用；它只负责 HTTP 取 token，不负责 WS 信令。
- 测试期采用已约定的 `ws://47.117.159.193:8080/talk/v1/ws`，握手使用 `talk.v1.json` 和服务端已支持的 Bearer token。
- 不把 WebRTC 的 BoringSSL 当成应用 TLS SDK。WSS/正式认证在上线前另行完成证书校验和 OpenSSL/BoringSSL 符号隔离验证；本阶段不宣称生产安全就绪。

## 5. 模块、线程与接口

```text
Qt5 主线程：界面 / 配置 / Qt 适配器
                 │ C API 命令
                 ▼
talk-core：Asio 控制线程
  WS 收发 / 请求超时 / 会话与房间状态 / 重连 / 模式与发言权
                 │ 异步投递
                 ▼
libwebrtc：signaling / worker / network 线程、ADM 音频回调
```

- core 事件先归并到控制线程，再由 Qt 适配器使用 queued connection 投递 GUI；core 本身不使用 QObject 或 Qt 信号槽。
- 音频回调中禁止网络请求、等待 GUI、文件 I/O 和长时间加锁；Qt 主线程禁止等待 SDP、ICE 或 WS 完成。
- C API 使用 opaque handle、固定宽度类型、UTF-8、版本化结构和回调；不暴露 STL、Qt 类型或 WebRTC 指针。
- API 覆盖创建/销毁、认证连接、入退房、静音、设备枚举/选择、播放音量、状态及统计；后续加入呼叫、发言权和主持人命令。
- 命令提交与最终结果分离，用操作 ID 关联完成事件；回调数据在回调返回前有效，Qt 适配器复制后再投递。
- 连接、房间和媒体协商均带内部 generation，退出/重连后丢弃过期回调；销毁顺序为停止新任务、取消请求/定时器、关闭 PC/ADM、回收线程，保证销毁返回后不再回调。

### C0：构建骨架和板端运行基线
1. 创建独立工程、RK/host-test presets、专用 triplet；构建 `libtalk_core.so`、`talk-cli`、Qt 最小窗口。
2. host-test 先运行不依赖真实媒体的协议/状态测试，不强行用 ARM 库在 x86 上执行。
3. 使用已有探针进行板端受控验证：先 `TALK_PROBE_FAKE_AUDIO=1`，观察实时收发、输出幅值、削波和欠载；真实声卡测试放到确认设备占用及现场条件后。
4. 检查 ELF、共享库导出、动态依赖和 GLIBC/GLIBCXX；验证 Qt 中文显示、尺寸和触摸输入。
5. Qt 优先接现有 Wayland 会话；以实测确认 `XDG_RUNTIME_DIR=/run`、`WAYLAND_DISPLAY=wayland-0` 是否适用，不直接切换 EGLFS 抢占 DRM。

**通过条件**：干净构建可复现；ARM64 核心库/CLI 正常启动；探针完成实时音频链路检查；Qt 窗口能在实机显示。offscreen 测试仅作补充，不替代屏幕验收。

### C1：信令、会话和房间
- 严格实现 `v/type/id/method/data` 封装，区分 `req/res/ntf`；注册服务器请求处理器后再入房。
- 实现 `session.hello/ping/refreshIce/bye`、`room.join/leave`、`media.setMute` 及成员/角色/退出通知。
- 正确处理服务器发起的请求，未知 method 回 501，未知字段忽略；消息大小上限与当前服务端默认 256KiB 对齐。
- 请求默认超时 10 秒；SFU 请求可配置 15 秒，但服务端下行请求期限以实际配置为准，不能假定客户端延长即可生效。
- 心跳与 resume TTL 使用 hello 应答值；实现有界发送队列、pending 请求清理、迟到响应过滤和退避重连。
- 初期声明 `platform=linux-arm64`、Opus、`aec=webrtc`、`p2p=false`；入房策略使用 `free/sfu`，初始静音。
- 握手成功后发送的是 `session.hello` 并接收 `res`，协议中没有独立 `welcome` 方法。

**通过条件**：板端 CLI 与 bot 同房互见；静音/离开/host 移交正确；过期 token、无房间权限、顶号、超时、断线恢复等正反例通过。

### C2：原生 libwebrtc 与 SFU 对接
- 创建共享 Factory/ADM/APM 及 send、recv 两条 PC；send PC 发送 `sendonly` offer，经 `sfu.publish` 获得 answer。
- `sfu.offer` 是服务端请求：服务器 SDP 使用 `sendonly`，客户端设置 remote offer 后生成 `recvonly` answer，并以原请求 ID 返回 `{sdp}`。接收 PC 不添加本地麦克风轨。
- recv 协商串行处理，维护 `mid → consumer/uid` 映射，处理 inactive、关闭、复用以及用户反复进出；不因静音重建 PC。
- recv offer 可能早于本端 publish 完成，必须独立处理，不能串成“publish 成功才允许订阅”的流程。
- SFU 不增加不存在的 trickle 消息；使用服务端完整候选和 libwebrtc ICE 检查建立连接。P2P 的 trickle 留到 C5。
- 音频目标为 48kHz 单声道、20ms、16～32kbps、FEC/DTX；SDP 的 `opus/48000/2` 是正常协商表达，不把它强改为 `/1`。
- 使用带真实 Opus 编解码的合成音源/PCM 检测器检查内容、时序和音量，而不是只统计 RTP 数量。

**通过条件**：RK 原生 M146 与 S2 建立 ICE/DTLS-SRTP，双向有正确音频内容；成员反复加入/离开不破坏 recv 协商；静音不触发 SDP 协商。现有 werift bot 的固定静音包仅用于信令/RTP 验证，不用于真人音质验收。

### C3：音频设备、AEC 与性能
1. 先读取声卡占用、PulseAudio 状态、mixer、PCM 能力及现有业务使用情况，确认 card0/card1/card3 对应的物理接口；曾观察到 card1 播放被占用，禁止直接停占用进程。
2. 使用可配置且稳定的设备标识映射到 ADM，采集与播放可分别选择；不把 card0 或 `hw:0,0` 固定为默认正确路径。
3. 默认验证 libwebrtc ALSA ADM；已有音频服务独占设备时，验证 PulseAudio ADM 接入该服务，不擅自停服务。两种后端均由配置明确选择并记录。
4. 测试设备支持的采样率/通道/格式、录音有效幅值、削波、播放路由及同时采放；设备与 48kHz 不一致时验证 ADM 的转换链路。
5. 默认软件 AEC3 + NS + AGC2 + 高通。单独调查 ES8311 `AEC MODE` 的驱动含义、回采接线和采样同步；仅在证据齐全且端到端测试通过后提供 `aec=hw`，硬件回采与硬件 AEC 分开认定。
6. 先耳机，再低音量外放，再双讲/远近场/音量变化；没有有效 AEC 前不直接运行高音量声学回环。
7. 记录 1 路及多路接收时 CPU、RSS、线程数、XRUN、端到端延迟、温度/降频；说明 CPU 百分比是单核口径还是整机口径，不沿用未实测的性能保证。

**通过条件**：真实麦克风与扬声器双向可懂、无持续削波/XRUN；外放回声可接受、双讲不明显吞字；受控局域网端到端延迟目标 <300ms，公网指标另行记录。

只有合成音源或一台板的回环通过，不能宣布真人双向音质通过；最终需现场人员及第二个支持真实音频的客户端配合。

### C4：Qt5 Widgets 界面
- C0 即建立 Qt 壳，C1～C3 期间可接入 mock 状态；C4 完成真实引擎联动，headless 不是最终用户交付形态。
- 连接页：服务器、用户标识、开发 token 入口、连接/错误状态。
- 房间页：输入/记忆房间 ID、加入/离开、成员及角色、静音状态；协议没有房间列表查询，不虚构在线房间列表功能。
- 音频页：设备枚举/选择、软件播放音量、音频后端、诊断信息；不默认修改系统级 mixer 或持久化全局音量。
- 状态栏：信令连接、媒体连接、当前模式、恢复状态、基础质量指标。
- 自由通话使用静音开关；PTT 控件在 C6 才启用，不能把本地按键静音冒充服务端抢麦。
- 关麦立即在本地停止发送；开麦必须收到服务端成功应答后恢复。失败、强制静音、退出均保持安全静音。
- 提供触屏友好布局、中文字体兜底；耗时操作异步化，窗口关闭时有序释放 core。

**通过条件**：用户只操作 Qt 界面即可完成入房、语音通话、静音、音量调整及退出，至少两端稳定运行 1 小时。

### C5：呼叫、P2P 与模式切换
- 对接 `call.*` 来电、振铃、接听、拒接、取消、挂断与超时状态。
- 服务端指定 offerer；实现 `p2p.offer/answer/candidate/state`，候选在 remote description 就绪前缓存，按 session 丢弃旧消息。
- 使用下发的 ICE servers；验证直连、srflx、TURN UDP/TCP，并通过 selected candidate pair 判断实际路径，不以端口可达代替中继成功。
- 按 TTL 提前刷新 TURN 凭证；强制 relay 和禁止 relay 的策略分别测试。
- `room.mediaMode` 切换采用先建后断；建立 SFU 后确认有效媒体，切换期间只播放一路，再按服务端确认流程关闭旧 P2P，失败保留仍可用链路并报告错误。
- S3 联调前必须冻结模式切换完成/旧链路关闭确认、失败回退的完整消息时序；当前草案未明确的通知不由客户端私自发明。
- 未完成 C5 或服务端不支持 S3 时维持 `p2p=false`；验证通过后才默认开启能力声明。

**通过条件**：内网/跨 NAT/强制 TURN 均接通；第三人加入触发 SFU 切换，目标断音 <500ms；取消来电、重复通知及过期 candidate 不污染当前通话。

### C6：PTT 与主持人控制
- 对接 `floor.request/release/state/revoked`、`host.grant/muteAll/kick/setPolicy`、`media.forceMute`。
- PTT 按下申请，获批才发音；松开、失焦、触控取消、断线或超时立即关闭本地发送并释放发言权。
- 处理“申请未返回就松开”和“迟到获批”竞态，禁止迟到应答重新打开麦克风；排队不等于获准发言。
- UI 展示持麦人、队列、占麦期限和权限状态；主持人按钮按角色启用，但最终授权始终以服务端为准。
- 对接 `room.activeSpeaker/audioLevels/subscribeLevels`，控制 UI 更新频率，避免通知淹没 GUI。

**通过条件**：两人竞争抢麦、排队、超时、强制收回、主持人变更和踢人全部有效；预建媒体链路上 PTT 按下到对端出声目标 <300ms。

### C7：恢复、弱网、长稳和交付
- WS 重连使用 1/2/4/8 秒、上限 15 秒的退避并带抖动；顶号/明确踢下线不自动反复重登。
- WS 断开时保留仍有效的 PC 和收听链路，麦克风安全静音；恢复后根据服务端确认恢复允许的发送状态，PTT 不自动重新抢麦。
- `resumed=true` 使用 room 快照，不重复 join；当前快照不包含本人完整静音状态，不能凭其他成员列表推断，必须显式同步并等待确认。
- 仅对同一存活实例尝试保留 PC 的 resume；进程重启走新会话。resume 失败或媒体状态失效时，有序重建，不盲目向旧 transport 绑定新 DTLS 状态。
- send ICE restart 使用原 PC 的新 ICE offer 经 `sfu.publish`；recv 调 `sfu.restartIce` 后应答新的 `sfu.offer`。测试协商失败、成员变化和重连同时发生的情况。
- 每 10 秒发送协议规定的 `sfu.stats` 通知，并保留本地细粒度统计。当前 S2 的通知处理尚未落地质量存储，不能把发送成功当成监控完成；与 S5 对齐字段单位和统计落点。
- 弱网矩阵覆盖 10%/20% 丢包、100ms 抖动、限带宽、短断网、服务重启；故障注入与真实 4G/路由切换单独安排，保留管理 SSH 通道。
- “5 秒恢复”从网络重新可用且故障已被检测后测量，单独记录断线检测耗时；现有 15/45 秒心跳不能保证所有黑洞故障都在发生后 5 秒内发现。
- 进行 24 小时长稳和 20 人房间规模测试，监测 RSS、句柄、线程、PC/Consumer 数量趋势；规模 bot 测试与真人音质测试分开。

**通过条件**：弱网语音可懂；可恢复故障满足定义后的恢复目标；24 小时无崩溃、死锁或持续资源增长；退出后不遗留会话和音频占用。
